The typed ingest endpoint accepts JSON strings, numbers, booleans, `null`, and arrays of strings. You do not need to serialize every property value as text or provide type and delimiter hints in the request.

Use typed ingest when your integration already works with structured JSON. The existing import endpoint remains available for integrations that use the legacy string-based entity format.

## Before you begin

You need:

- The customer-facing ID of the target source.
- A tenant-level Application with the `write:sources` scope.
- Access to the target source, or access to all sources, in the Application's resource grants.

See [Application access tokens](/api-reference/authentication/application-token) to request a bearer token for the tenant audience.

<Warning>
  A token created by the legacy data-provider credential exchange has the `import-datasource` permission. The typed endpoint requires `write:sources`, so use a tenant-level Application token instead.
</Warning>

## Send typed entries

Call `POST /sources/{sourceId}` with one or more entries. Every entry is an upsert. The typed endpoint does not accept a delete flag.

```bash
curl --request POST \
  --url "https://api.occtoo.com/sources/${OCCTOO_SOURCE_ID}" \
  --header "Authorization: Bearer ${OCCTOO_ACCESS_TOKEN}" \
  --header "Content-Type: application/json" \
  --data '{
    "entries": [
      {
        "id": "sku-123",
        "properties": [
          { "id": "tags", "value": ["summer", "sale"] },
          { "id": "price", "value": 100.111 },
          { "id": "publishedAt", "value": "2026-01-01T00:00:00Z" },
          { "id": "inStock", "value": true },
          { "id": "name", "value": "Blue chair", "language": "en" }
        ]
      }
    ]
  }'
```

Use `https://api-test.occtoo.com` when testing against the test environment.

## How values map to source types

If a property already has a configured type, its JSON shape must match that type.

| Source property type | Accepted JSON value |
| --- | --- |
| `Text` | String |
| `LocalizedText` | String with `language` |
| `List` | Array of strings |
| `LocalizedList` | Array of strings with `language` |
| `Boolean` | Boolean |
| `Timestamp` | ISO 8601 string |
| `Integer` | Whole JSON number within the 64-bit integer range |
| `Decimal` | Finite JSON number |

Localized properties require `language`. Non-localized properties reject it. A `null` value clears a configured property by storing an empty value.

<Note>
  A timestamp string is only treated as a timestamp when the source property is already configured as `Timestamp`. An unconfigured string is inferred as `Text` or `LocalizedText`.
</Note>

## Type inference for new properties

When a property has no configured type, Occtoo infers it from all values for that property in the request:

| JSON value | Inferred source type |
| --- | --- |
| String | `Text`, or `LocalizedText` when `language` is present |
| Array of strings | `List`, or `LocalizedList` when `language` is present |
| Boolean | `Boolean` |
| Whole number | `Integer` |
| Number with a fractional part | `Decimal` |

Integer and decimal values in the same request are promoted to `Decimal`. Other incompatible JSON shapes cause the entire request to fail. Occtoo cannot infer a new property from only `null` values.

New list properties use `,` as their delimiter. Existing list properties keep their configured delimiter. List elements cannot contain that delimiter.

Property IDs are matched case-insensitively and stored in lowercase. The response reports inferred properties in `newPropertiesFound`. The ingestion worker registers them asynchronously, so they may not appear in Configuration immediately.

## Accepted response

A valid request returns `202 Accepted`:

```json
{
  "correlationId": "83b538a7-df7c-4cf4-b988-cd3b71c4cd90",
  "sourceId": "products",
  "acceptedAt": "2026-08-13T10:15:30Z",
  "acceptedEntryCount": 1,
  "newPropertiesFound": [
    {
      "id": "tags",
      "type": "List",
      "delimiter": ","
    }
  ]
}
```

`202 Accepted` means the complete batch passed validation and was queued. Downstream entry processing and new-property registration may still be running. Keep `correlationId` for diagnostics. Do not retry a successful request because the data is not visible immediately.

## Validation and errors

Validation is all-or-nothing. If one entry or property is invalid, the API rejects the complete request with `400 Bad Request`. Validation errors use request paths as keys:

```json
{
  "title": "One or more validation errors occurred.",
  "status": 400,
  "detail": "Invalid typed ingest payload",
  "instance": "/sources/products",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "errors": {
    "entries[0].properties[1].value": [
      "Property 'price' is configured as Decimal; expected a JSON number but got string."
    ]
  }
}
```

The endpoint can also return:

| Status | Meaning |
| --- | --- |
| `401` | Authentication is missing or invalid. |
| `403` | The caller lacks `write:sources` or is not granted the source. |
| `404` | The source does not exist or cannot be resolved. |
| `409` | The source is being purged or is in another conflicting state. |
| `429` | The tenant request-rate budget is exhausted. Respect `Retry-After` when present. |
| `500` | The ingest operation failed unexpectedly. |

Retry `429` and transient `5xx` responses with bounded exponential backoff.
